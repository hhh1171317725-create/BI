# Bid Monitor

Entry: `/tools` -> 出价监测 (`/bid-monitor.html`). No extra Nginx route is required. The existing static file handler serves the page; Spring handles `/api/bid-monitor/**`. The snapshot endpoint automatically creates `bid_monitor_snapshots` on first use; the database user needs CREATE TABLE permission.

### gap 与大航海账户关联（2.5.0）

- 以出价监测已加载数据的统计结束日期为基准，取之前3个完整自然日（不含结束当天）。例如统计结束日为9月8日，gap区间为9月5日至7日；修改日期输入框但尚未重新查询，不改变已有数据的gap区间。
- 按广告账户ID `advertiser_id` 关联大航海“账户ID”，不使用创量内部ID或名称模糊匹配。沿用大航海日报账户分摊口径：任务结算数、注册数按账户消耗占比分摊；先汇总同一账户同一天的指标，再计算每日结算数/注册数，最后取有效日的算术平均值，不是三天总量比。
- 无记录或注册数为0的日期不参与平均。全部无效或账户未匹配时gap为null，相关收益指标显示`--`，不默认使用1；有注册但结算为0的日期按0计入平均。gap可大于1，不自动截断。
- 明细新增gap和实际单价；原单价保留。实际单价=原单价×gap，佣金、ROI、盈亏线及出价利润率均基于实际单价计算，汇总和CSV同步。鼠标悬停gap可核对逐日分子、分母和有效天数。
- 每次加载计划（查询、导入、快照）重新读取gap；“刷新gap”可在大航海数据更新后重新计算。读取失败清空旧gap并提示重试，避免使用另一统计期的系数。
- 钉钉预览及定时推送使用相同日期和系数；未匹配gap的条目显示`gap缺失`及不可计算利润率，不沿用原单价。无需更改原有任务价格配置或数据库结构。
- 验证：`./mvnw clean package`、`node --test scripts/bid-monitor.test.cjs`、`node scripts/bid-monitor-ui-test.cjs`。包括每日均值、同日聚合、零分母、零gap、实际单价及钉钉一致性、界面刷新和CSV回归；不触发真实推送。

### 发布步骤

Run from a server terminal independent of the website:

```bash
cd /www/wwwroot/BI
git pull --ff-only origin main
export JAVA_HOME=/www/server/java/jdk-21.0.2
export PATH="$JAVA_HOME/bin:$PATH"
./mvnw package && systemctl restart dahanghai-analysis
```

Only restart after a successful build. Administrators can enable `bidMonitor` for operators in the existing tool permission dialog. All endpoints enforce login and tool permission. The query-and-enable action saves encrypted credentials for reuse and scheduling; snapshots contain only allowlisted plan data. Snapshot reads always use the current website user; configuration changes also verify the website user bound when the page was loaded.

## DingTalk Task TOP5 (2.2.1)

- Open the 钉钉任务 TOP5 section below saved task prices. Select 1-10 saved tasks and enter the destination robot Webhook, optional signing secret, and matching security keyword. Default daily time is 18:00 in Asia/Shanghai. Enable 定时推送 and save. Different website users have independent configurations; this feature does not use the shared email-forwarding robot.
- Robot setup references: [official custom robot access](https://open.dingtalk.com/document/robots/custom-robot-access) and [security settings](https://open.dingtalk.com/document/robots/customize-robot-security-settings). Webhook and signing secrets are stored as an owner-bound encrypted bundle using the existing bid-monitor key. They are never returned to the browser. Blank credential fields retain saved values; changing a robot requires a new signing secret or explicitly selecting 不使用加签. Clearing the robot removes its credentials and disables notification scheduling, without deleting data sync credentials or task prices.
- 预览 TOP5 shows the exact per-task message without posting it. 立即推送 requires confirmation and uses the same saved configuration and snapshot as scheduled sending. It is a real send, not a sandbox, and can duplicate the daily message if used intentionally. Manual sends are limited to one attempt per five minutes per website user.
- Each selected task gets one text message containing up to five plans, sorted by total spend descending. Matching uses saved account-name keywords and excludes ambiguous matches. Scope is the current user's complete snapshot for the configured creation window. A task with fewer than five matches sends its actual count; no matches are explicitly labeled as absent. Only same-day snapshots no older than 20 minutes are accepted. Keep the existing ten-minute server sync enabled; historical queries and Excel imports do not become scheduled notification data.
- Messages use a compact two-line layout compatible with desktop and mobile DingTalk: a task title, circled rank, plain signed 利润出价 percentage and thousands-separated metrics on line one; optimizer plus shortened 账/计 ID labels on line two. Plans have no blank line between them, while tasks retain one separator line. Return ratio = conversions / registrations; zero registrations produce --. Names, ROI, other financial metrics, timestamps and explanatory footers are omitted from group messages. The full website table and its calculations are unchanged. The configured security keyword may add one required prefix line.
- The server checks due notifications every 15 seconds using a bounded two-worker pool. Schedule and delivery attempt state are persisted separately from data-sync scheduling in the same per-user JSON record. The database must support JSON_EXTRACT. No new tables or runtime keys are required. The process can recover a missed slot only within 30 minutes of that day's configured time; older missed slots are skipped rather than sending unexpected catch-up messages.
- A durable daily claim is recorded before external delivery. Restart, concurrent schedulers and uncertain transport outcomes cannot automatically replay that daily batch. Partial failures keep the acknowledged message count; remaining tasks are not automatically retried that day. A crash after claiming may leave an uncertain result that must be checked in the group. Exactly-once delivery cannot be guaranteed by a webhook. Config/price/permission changes are checked before each message; messages already in flight cannot be recalled. Snapshot freshness, revoked access or invalid credentials result in a visible failure without sending stale data.
- Deployment requires `./mvnw package` and a service restart because these endpoints and the daily scheduler are new. Merely pulling the frontend files is not sufficient.

## Server Scheduled Updates (2.1.3)

1. No extension is required. Stop the old extension's bid synchronization, or disable that extension if it is no longer needed. The new page talks only to the BI backend.
2. Enter Cookie, client-user and main-user-id from the same authorized Chuangliang session. Each operator uses their own website account and their own upstream credentials. No sample or historical credentials are automatically saved.
3. Updates run every 10 minutes. Creation scope is Beijing today minus three days through today, inclusive (four calendar dates): September 4 reads September 1-4. Existing schedules adopt the interval on the next save or successful run. Click 查询并启用定时更新 to save credentials, query immediately and schedule the next server run in 10 minutes. Blank Cookie/client-user/main-user-id values reuse this website user's saved values; changing the upstream identity requires a fresh Cookie. Plaintext is cleared after saving and is never stored in browser storage. Refreshing the page restores saved identity fields, never the Cookie.
4. 保存并启用 remains available to queue an immediate server run (approximately 5 seconds), while 查询并启用定时更新 performs its first query directly through the owned saved-credential endpoint. Subsequent manual queries with unchanged saved credentials do not postpone or invalidate an enabled schedule. Schedules persist in MySQL and continue with Chrome closed. 立即同步 queues another run; 停止同步 cancels future scheduling and invalidates in-flight commits. 清除保存凭据 removes the encrypted Cookie and query revision while preserving task prices and the last snapshot.
5. Each run reads Beijing's current-day statistics and follows every 100-row page until it has collected the exact upstream total. The creation window remains today minus three days through today, inclusive. The snapshot records `created_window_all`; exact provider duplicates are audited and removed, while an incomplete, changing, empty, or over-100,000-row result is rejected without replacing the previous snapshot.
   While a manual or scheduled query is running, the status endpoint exposes structured progress. The page refreshes it every two seconds and shows current/total pages, collected/total plans, elapsed time, average plans per second and estimated remaining time.
6. Failed authentication, upstream rejection/verification, undecryptable credentials or revoked website tool access pause server synchronization without replacing the last successful snapshot. Network failures and incomplete/duplicate/empty data preserve old data and retry in 10 minutes without requiring credential re-entry. Correct expired credentials and enable again; login, verification and upstream permissions are not bypassed.
7. A bounded two-worker pool performs collection outside the Spring scheduler thread. A database row lock and revision token guard each claim/commit. Interrupted jobs have a three-minute lease before recovery. Successful page progress renews the lease, checks ownership/permission and exposes the collected/total count; stopping prevents further pages and commits. Permission and Beijing date are checked again before saving. Enabled server jobs reject old extension snapshot uploads to avoid overwrites.
8. Visible pages poll status every 2 seconds while open, independently of server scheduling. Manual queries matching today's default statistics/creation window follow subsequent successful server snapshots automatically. Historical queries and Excel imports are not replaced automatically. 读取最新快照 explicitly loads the latest owned snapshot; its timestamp and statistical date remain visible. Every saved-credential page request verifies the website user and credential revision before and after fetching, rejecting account switches or cleared/replaced credentials mid-query.

### Credential Storage And Deployment

- The database user needs CREATE TABLE permission for bid_monitor_server_sync and bid_monitor_snapshots. Settings, due time and status are persisted per website user. API responses never include encrypted or plaintext Cookie values.
- AES-256-GCM uses a random nonce per save and binds ciphertext to the website user ID. The 32-byte key is created in DHH_RUNTIME_DIR/bid-monitor.key (default .runtime/bid-monitor.key). On POSIX it is created owner-only. The service user must be able to read/write this directory. Keep it outside the Nginx static root.
- Back up the key securely alongside database backups. Do not commit it or delete the runtime directory during deployment. If the key is lost, restore it or re-enter credentials for affected users. Multiple application instances must share the same key and MySQL database.
- Use HTTPS for the website and keep its normal authentication enabled. Encryption at rest is not protection against a compromised application server.
- Credentials remain subject to expiry and upstream access policy. Local authorized HTTP success does not guarantee that the deployment server's IP will be accepted. A server-side refusal requires checking the provider's permissions or supported integration, not fingerprint evasion.

## Data And Interpretation

- In 任务结算价格, add a task name, a substring to match in the upstream account name, and its customer settlement price per registration. Save task prices. Rules are stored per website user with optimistic conflict detection and never change another user's rules. Up to 50 tasks are supported. Matching is case-insensitive; zero matches, multiple matches or invalid prices suppress ROI for those plans rather than silently choosing a price. There is no global fallback price. The task filter, search, table and CSV use the same resolved prices.
- `convert_cnt / active_register` is the observed return ratio; it is not necessarily the configured return rate, especially during delayed attribution.
- This assumes `cpa_bid` targets exactly the conversion counted in `convert_cnt`, and all registrations are billable at the entered price. Deep-conversion and dual-bid campaigns need a different analysis.
- ROI now uses commission / cash spend, rounded to three decimal places. Commission = registrations * task settlement price. Conversion cost = total spend / conversions. A plan receives a calculated grant only when conversion cost > 1.2 * bid AND conversions > 6; then grant = total spend - bid * conversions, otherwise grant = 0. Cash spend = total spend - calculated grant. Equality at either threshold does not qualify. Binary-rounding noise at the 1.2 boundary is ignored. Grants are estimates from this rule, not confirmation that the platform has credited them. Unknown required inputs or zero cash spend give -- rather than Infinity. Zero conversions imply no grant, but ROI can still be calculated when commission and positive cash spend are known.
- 出价利润率 compares the bid to its break-even line: break-even bid = task settlement price / (conversions / registrations); bid profit rate = (break-even bid - current bid) / break-even bid. For a break-even bid of 100, bids of 80 / 100 / 120 imply 20% / 0% / -20%. This is a bid-based margin, not cash ROI minus one. The display uses a plain signed percentage with two decimals and no direction arrow; an undefined break-even line gives --. Hovering shows the break-even bid; ROI hover shows commission, calculated grant and cash spend. CSV includes these calculation inputs too.
- Date ranges including today are marked provisional. Yesterday can still have delayed attribution; review after the project's attribution window closes.
- Results describe the dates captured when data was fetched/imported, not subsequently edited date controls.
- The result selector supports plan detail, optimizer, task, and optimizer × task views. Every aggregate includes total plans, plans created on the current Beijing date, plans with spend greater than zero, unique accounts, price coverage, spend, conversions, registrations, commission, cash spend/profit, estimated ROI, and bid profit rate. CSV export follows the selected dimension. Provider plan creation time is retained in the allowlisted snapshot solely for these counts.
- Both manual queries and scheduled sync request every page by immutable unique plan ID descending and validate the exact upstream row total, up to the 100,000-row safety limit. Spend sorting is intentionally applied locally after collection because sorting live upstream pages by changing spend can move plans between pages. Exact duplicate plan rows returned by the provider are counted and removed before the unique-plan snapshot is saved; missing pages and changing totals still fail without replacing previous results. Excel import is unchanged. `getSum` is not mixed with list data; summaries are calculated from the currently filtered rows. Grant eligibility is evaluated for each plan before aggregation. Aggregate financial fields use only plans with matched task prices, and the price-coverage column plus cell tooltip discloses that scope; unmatched plans remain included in plan, account, spend and event totals and are never treated as zero-revenue plans. Aggregate ROI is total commission divided by total cash spend for the matched subset, not an average of plan ROIs. Aggregate bid profit rate is commission-weighted across rows with valid break-even lines. Optimizer cash profit is matched-subset commission minus matched-subset cash spend.
- Result sorting is controlled directly from every table header. Numeric fields start in descending order, text fields start in ascending order, and clicking the active field toggles direction. Missing values always remain at the end.
- Excel import reads the first sheet with header row first. Required columns: `stat_cost`, `convert_cnt`, `active_register`, `cpa_bid`, or 消耗、转化数、注册数、出价. Use a plan-level period aggregate without totals or duplicate rows, and select its actual period before importing. Keep account/plan IDs formatted as text.
